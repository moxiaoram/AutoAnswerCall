# AutoAnswerCall 1.17.5：系统自动接听与人工介入测试

**新流程：系统自动接听 → SpringBoard 检测已接通并尝试本机音频播放 → InCallService 显示「停止播放」→ 点击停止本机音频，通话保持连接、人工可以继续讲话。**

**重要：这不是通话上行注入实现。** `AVAudioPlayer` 只启动本机播放器，无法保证来电方听见音频。锁屏 InCallService 窗口、RootHide 共享文件权限和通话音频路由必须真机确认。

开启前请先在 iOS 辅助功能中打开系统「自动接听通话」；插件设置开启「启用插件策略」「接通后播放本地音频」「系统接听后本地音频＋停止按钮」（默认关闭），选好音频。按下通话界面的「停止播放」不会挂断电话或改变麦克风状态。详细修改见 `FIXES-1.17.5.md`。

## 1.17.2 Live-button discovery + simulated tap is the primary answer strategy — NOT device-verified

1.17.2 keeps every guard from 1.9.x through 1.16.0 and replaces the *primary* answer strategy. Method-name keyword discovery (the 1.15.0 ACTION/ACCESSOR classification) is **retained but known to be insufficient**.

DEVICE EVIDENCE THAT DROVE IT (the user's 1.16.0 chunked-transport read-back on the iOS 17.3 RootHide device, quoted because it is the authoritative record):
- ALL THREE hosts are injected: `springboard pid=9061`, `mobilephone pid=9145`, `incall pid=9146`.
- ALL THREE report `role=LOG-ONLY` with `answerPaths=0`: incall `0 个 ACTION (其中已挂钩 0、NSInvocation 候选 0)，8 个 ACCESSOR 挂钩（仅证据）`; springboard the same shape; mobilephone reads `keys=0` (fail-closed, the config is not visible to it).
- The state-slot transport works (`校验=通过`, e.g. incall 88 slots / 525 bytes). The name-embedded chunk channel cannot be received because Darwin notifications cannot be wildcard-registered (as documented in 1.16.0).
- CONCLUSION: the "class-name + selector-keyword" discovery strategy finds **no** real answer action anywhere, and the reason is structural: the real answer is a UI BUTTON whose response goes through the UIControl action mechanism (`sendActionsForControlEvents:`), so its method names never contain `answer`/`accept`. Keyword matching can never find it.

- TASK 1 — LIVE BUTTON DISCOVERY + SIMULATED TAP (`AACButtonScan.h`, new file). During an incoming call, in each host that has an incoming-call UI (InCallService first, then SpringBoard, per the existing ownership table — the role table is unchanged), the module traverses the LIVE view/responder hierarchy: every `UIWindowScene` window → responder chain (≤12 up) → root view controller (`presentedViewController` + `childViewControllers`) → view tree. Bounded: **≤6000 nodes, depth ≤40, 1.5 s time budget, ≤32 candidates**, and the report states whether the budget was exceeded. It collects candidate `UIControl` instances (including `UIButton` and any `UIControl` subclass) and logs EVERY candidate with class, accessibility identifier/label/value, button title, frame, tint/background colour, green score, red-dominance, left/primary flag, sibling control count, which signal matched, blacklist status and tappability — so the next device test is conclusive even if nothing is tapped.
- SIGNALS, in priority order: `accessibilityIdentifier` containing `accept|answer|acceptcall|接听|应答|answer_call` > `accessibilityLabel` > `accessibilityValue` > button title (`titleLabel.text` / `currentTitle`) > known localisation substrings > (weaker) a green-tinted control (`backgroundColor` or the 1×1 average colour of `backgroundImage`) that is the left/primary button of a two-button incoming layout (same superview, ≥2 `UIControl` siblings).
- TAP MECHANISMS, tried in this order and logged with the one actually used: **(1)** `[control sendActionsForControlEvents:UIControlEventTouchUpInside]`; **(2)** if that event has no registered target/action pair at all (so it could not have triggered anything), `sendActionsForControlEvents:UIControlEventTouchUpInside|UIControlEventTouchDown`; **(3)** as a last resort, the control's own pairs discovered via `allTargets` + `actionsForTarget:forControlEvent:` invoked through `NSInvocation` with default arguments (object/pointer = nil, scalars = 0; at most 3 explicit arguments, only types whose default value can be constructed safely).
- SAFETY GATES: the decline/reject/hang-up blacklist (`decline`, `reject`, `hangup`, `hang up`, `end call`, `disconnect`, `dismiss`, `ignore`, `voicemail`, `拒接`, `拒绝`, `挂断`, `结束…`) is applied to accessibility identifier, label, value AND title, and a red-dominant control is blacklisted too, so a red "decline" button can never be tapped — blacklisted candidates are recorded but never selected. A candidate is only tappable when it is `enabled`, `userInteractionEnabled`, not hidden, `alpha>0.01` and has a window. Every tap goes through `@try`.
- SINGLE TAP: one tap per call UUID per host (`AACButtonClaimTapUUID`) plus a **1.2 s settle window**: a host with higher-priority peers broadcasts its claim, waits the window and then yields if it has observed a higher-priority host really tapping (the new `com.autoanswer.call.buttontap.<tag>` notification), so two hosts can never tap the same call. Kept unchanged: the per-UUID single-submission claim, the delay + re-verification (call still incoming/unconnected/not-ended, settings re-read, stop generation), fail-closed config, exclusion list, records, discovery files, chunked transport, ownership rules and "no double tapping".
- TASK 2 — HONEST DIAGNOSTICS: the discovery/classification output gains a **BUTTON candidates** section (distinct from the ACTION/ACCESSOR method classification), written into `aac-<tag>.discovery.txt`, logged line by line (so the summary budget cannot truncate it) and published through the existing chunked/state-slot transport (`AACSBHostMessageText`). It reports nodes visited, candidates found, every candidate's signals, the chosen control, the tap mechanism used and whether the call subsequently reported connected. The Settings text states explicitly that method-name keyword discovery is retained but known insufficient and that the button path is the primary strategy.
- HONEST LIMITATIONS: UNVERIFIED on device. No install, no call, no credential in any artifact. What a successful tap mechanism means is only that the event was dispatched — the call is reported connected ONLY when `CXCallObserver` reports `hasConnected`. The settle-window handshake is a local design, not a device-verified fact.

## 1.16.0 Chunked cross-process message transport (payload inside Darwin notification names) — NOT device-verified

1.16.0 keeps every guard from 1.9.x through 1.15.0 and adds a second, additive transport so that InCallService's discovery/classification can be seen even though its files and its CFPreferences writes are unreadable from the Settings process.

DEVICE EVIDENCE THAT DROVE IT (the user's 1.15.0 run on the iOS 17.3 RootHide device, quoted because it is the authoritative record):
- process-probe page: `incall (com.autoanswer.call.probe.incall) 到达 2 次；最近 23:08:13` and `springboard 到达 2 次`. So the InCallService dylib IS injected and its probe notifications DO arrive cross-process. The earlier "incall never announced" was a timing artifact (that process only runs during calls).
- host read-back page: `Hosts = ( springboard )`; `[incall] 本进程未读到该宿主的任何键`; both real plist paths reported 不存在/不可见 by the Settings process, yet Settings read 12 keys of the same domain. So the file/CFPreferences channel only works for hosts that share the same container/preferences context (SpringBoard).
- CONCLUSION: the only proven cross-process channel is Darwin notifications, and their NAMES are arbitrary strings.

- TASK 1 — CHUNKED IN-NOTIFICATION-NAME TRANSPORT. Every host publishes a bounded discovery summary (the same content as the host report: host tag, role, answerPaths, actionMethods, accessorMethods, classification counts, and the HOOKED/INVOKABLE lists) through two additive channels:
  - **name-embedded channel**: the text carries a self-describing envelope header (`AACMSG1 channel=name tag=… kind=… pieces=… bytes=… crc32=… truncated=… utc=…`), is base64url encoded and cut into at most **12 chunks of at most 900 base64url characters** (900 is a multiple of 4; no `/`, no `+`, no `=`, no NUL, so the name stays valid): `com.autoanswer.call.msg.<tag>.<seq>.<total>.<base64url-chunk>`, plus the order/structure name `com.autoanswer.call.msg.<tag>.<seq>.<total>` and the explicit end marker `com.autoanswer.call.msg.<tag>.end.<total>`. Hard total cap **12288 decoded bytes** with an explicit `…<msg-truncated>` marker.
  - **state-slot channel** (the half a receiver can pre-register): the same text is packed into 96 fixed names `com.autoanswer.call.msg.<tag>.w.<0..95>`, each 64-bit notification state carrying 6 payload bytes + a 16-bit generation, committed last by `com.autoanswer.call.msg.<tag>.hdr` (generation + byte length). Hard cap **96 × 6 = 576 bytes**.
- RECEIVER: Darwin notifications cannot be wildcarded, so the Settings process registers only the names it can enumerate — the structure names (78 per tag) and the end markers (12 per tag) — and reads the state slots on demand with `notify_register_check`/`notify_get_state`. It reassembles by (tag, seq, total), verifies generation, length and CRC32, keeps a bounded 8-entry ring per tag, persists the verified text to `aac-<tag>.host-messages.txt` next to the existing shared-log candidates, and shows it on the new Settings entry **跨进程分片消息（Darwin 名内载荷）** (per tag: chunks received/total, last update, completeness, decoded bytes, reassembled text). HONEST LIMIT: the chunk *content* of the name-embedded channel lives inside the name and therefore cannot be pre-registered, so that channel normally yields only arrivals/completeness and 0 decoded bytes — this is stated on the page itself, and the content comes from the state-slot channel. When nothing was received the page says the transport was **not observed**; it never claims a host is not injected.
- TASK 2 — REQUEST ON DEMAND: `com.autoanswer.call.msgrequest.<tag>` is registered by every host and makes it republish its summary immediately, so InCallService's data can be fetched right after a call instead of waiting for the 20 s timer. Status codes are reported as returned (`notify_post` result 0 means delivered to notifyd, not confirmed received).
- NO CHANNEL WAS REMOVED: the multi-candidate file channel, the `com.autoanswer.call.hostreport` domain read-back, the per-process probe/pong names, the discovery files and the run-log export all stay exactly as they were; the new transport is purely additive. Everything is bounded (chunk cap, total cap, slot cap, ring cap).
- TESTS: `tests/chunkmath.c` is a pure-arithmetic unit test of the framing (chunk count/lengths, seq/total validity, base64url alphabet, completeness mask, state packing, CRC-32 known vector) compiled and run by CI; `tests/source_checks.py` and `tests/deb_check.py` assert the transport, the request-on-demand name, the Settings entry, the `host-messages.txt` export and that no channel was removed.
- HONEST LIMITATIONS: the transport is UNVERIFIED on device. The next decider is whether the Settings page shows InCallService chunks (state-slot channel complete + CRC verified) and what its discovery says. No install, no call, no credential in any artifact.

## 1.14.0 Ownership demotion fixed: a probe is not ownership (NOT device-verified)

1.14.0 keeps every 1.9.x/1.10.0/1.11.0/1.12.0/1.13.0 guard (fail-closed `ConfigVersion` validation, plugin stop latch plus explicit resume, mode 2, exact-match exclusion list, decimal seconds editor, audio library, records list, icon, multi-path shared log, per-process Darwin probes, host table with per-host probe/pong/discovery names, the relaxed hook ABI gate with per-return-type thunks and bounded NSInvocation candidates, per-method outcome reporting, corrected CallKit error meanings, run-log export/share, four-bundle lowercase-only filter) and fixes the one thing the 1.13.0 device run exposed: the host that could answer handed the answer to a host that could not.

DEVICE EVIDENCE THAT DROVE IT (the user's real SpringBoard shared log; quoted because it is the authoritative record):
- 1.12.0 run: `matchedClasses=103 hookedMethods=0 rejected=8 role=OBSERVER` — the old narrow hook ABI gate really did block everything.
- 1.13.0 run at 14:03:05: `matchedClasses=150 hookedMethods=4 invokable=5 rejected=0 role=OWNER` — the relaxed gate WORKS; real answer-path methods are now hooked/invokable.
- real incoming call at 14:05:08 was detected (`Call 908FA104-... outgoing=0 connected=0 ended=0`) and the configured 6 s delay was scheduled correctly.
- BUT at 14:05:09 the host re-evaluated ownership and DEMOTED ITSELF: `SpringBoard 接听归属角色：OBSERVER 仅观察与记录（观察者：接听由 InCallService 负责（incall 的探测通知在 90 秒内到达过本进程（存活证据））；本宿主只观察并记录）`, then `observer only, answer owned by incall`.
- the call was never answered; InCallService never acted (its own host found nothing / never submitted); at 14:05:30 `Answer request observation timeout`, at 14:05:36 the call ended.

ROOT CAUSE: ownership demotion triggered on PEER PROBE PRESENCE — a probe seen within 90 s was treated as proof that the peer would answer. Presence proves only that the peer process exists. It does not prove the peer found a hookable/invokable answer path (a host whose discovery found nothing never broadcasts a claim at all), that it claims ownership, or that it will submit. So 1.13.0 gave the answer to a host that could not answer while the host that could answer went silent.

- DEMOTE ONLY ON AN EXPLICIT CLAIM (`AACAnswerHost.h`): `AACAnswerHostRoleForTag(tag, answerPaths, …)` demotes only when a strictly higher-priority answer host has actually broadcast the existing `com.autoanswer.call.owner.<tag>` notification **and** that claim is still inside the bounded `AACAnswerClaimFreshSeconds` (90 s) window (`AACAnswerPeerClaimReason`, `AACAnswerHigherPriorityOwnerClaimed`). The claim name and its payload-less semantics are unchanged (arrival asserted only). `AACAnswerPeerPresenceReason` survives for reporting, but its value is no longer admissible as a demotion basis, and the code says so at both ends.
- PEER PROBE PRESENCE CAN NEVER DEMOTE: a probe is emitted by every injected module, including one whose discovery found nothing, so it is presence evidence only. It still appears in the recorded reason text — explicitly labelled `仅存活证据：只证明该进程存在，不构成归属、也不代表它会接听，因此不触发让出`. A claim, by contrast, is posted only inside `AACSBStart` when the host decided it is OWNER, i.e. only by a host that really holds answer paths.
- DURABLE REASON FOR EVERY DECISION: each role decision carries a reason string (`AACSBRoleReason`, mirrored into the discovery file as `# roleReason=` and into every log line via `AACSBClaimReasonText`). OWNER reads `接听负责宿主：<host> 持有 N 条运行时发现的接听路径（HOOKED/INVOKABLE），且 90 秒内没有任何更高优先级的接听宿主广播过明确的接听归属声明…（角色表 …）`; OBSERVER names the claiming owner and the claim itself.
- IF WE ARE THE ONLY HOST WITH ANSWER PATHS WE ARE OWNER AND REALLY SUBMIT: the role is logged at discovery time (and inside the discovery file) and logged AGAIN immediately before submitting (`接听归属判定 call=… owner=… role=… why=… submitted=yes/no`), so the shared log states at both moments which host owns the answer and why.
- BOUNDED SAFETY TAKEOVER (at most once per call UUID): if a higher-priority host did claim ownership but, `AACAnswerTakeoverIdleSeconds` (12 s) after our own delay expired, the call is still incoming/unconnected (no submission evidence, no connection), the lower host may take over exactly once, logging `takeover after idle higher-priority owner`. The takeover runs the SAME submission body (`PerformAnswer`) and therefore still passes `AACSBClaimAnswerUUID`, so no UUID is ever submitted twice by this host; a second takeover attempt for the same UUID is refused (`AACSBClaimTakeoverUUID`, `AACSBHasTakenOverUUID`).
- KEPT UNCHANGED: per-UUID single submission, recursion guard (`AACSBDepth`/`AACSBInvoking`), exact-normalised exclusion list, fail-closed configuration, stop latch + explicit resume, delay seconds, records, discovery file, per-method outcome reporting, log export/share, host table, four-bundle lowercase-only filter, no hardcoded private class name, the one clearly-labelled public-transaction diagnostic attempt.
- NEXT TEST IS CONCLUSIVE (Task 2): the discovery file and the log now start with a compact `HOOKED list` block (class + selector + mechanism, plus the invokable-by-invocation candidates and `HOOKED_TOTAL`), emitted line by line and always visible; the digest that used to be truncated at 4000 chars in one (itself 2000-char-capped) log line is now emitted in bounded chunks with a 6000-char total budget (`AACSBLogDigest`), and the same block is written FIRST into the discovery file. Plus exactly one `接听归属判定 … owner=… why=… submitted=…` line per incoming call.
- HONEST LIMITATIONS: still UNVERIFIED on device. The fix makes the 1.13.0 failure mode (a host with 4 hooked methods demoting itself to a peer that never acted) impossible, and the bounded takeover covers the remaining "peer claimed but stayed idle" case. But whether the hooked/invoked path actually answers the call can only be decided by the next device call: the decider is the logged line `接听归属判定 … owner=… why=… submitted=yes/no` plus `hasConnected`. The claim notification carries no payload, so "the same call UUID" for the takeover rule is inferred from claim freshness at the moment our delay expires — that limit is stated here and in the code.

## 1.13.0 Relaxed hook ABI gate + full run-log sharing (NOT device-verified)

1.13.0 keeps every 1.9.x/1.10.0/1.11.0/1.12.0 guard (fail-closed `ConfigVersion` validation, plugin stop latch plus explicit resume, mode 2, exact-match exclusion list, decimal seconds editor, audio library, records list, icon, multi-path shared log, per-process Darwin probes, per-host probe/pong/discovery names, deterministic single-owner role table with a per-UUID submission guard, artifact checks) and fixes the two things the last device test exposed.

DEVICE EVIDENCE THAT DROVE IT (iOS 17.3 RootHide, user's screenshots): the SpringBoard module is injected and its probes/pongs arrive, `MobilePhone` and `InCallService` never announced themselves, the incoming test call WAS detected by SpringBoard with the correct delay policy, and then the record said `未发现可调用的 UI 接听路径（仅日志）` while the public transaction fallback failed with `com.apple.CallKit.error.requesttransaction` code 1. Since nothing was hooked at all, the hook ABI gate itself — not the class list — was the most likely reason nothing could answer.

- HOOK ABI GATE RELAXED (`AACSpringBoard.h`): 1.12.0 hooked only `(self,_cmd)`-shaped, void-returning methods because its replacement had a fixed C signature. That gate is gone. The accepted set is now **zero explicit arguments with ANY return type a fixed thunk can forward correctly** (void / BOOL / object / integer / float), each with its own thunk, so the saved original IMP is called with the right signature and behaviour is unchanged (`AACSBAnswerHook`, `AACSBAnswerHookBool`, `AACSBAnswerHookObject`, `AACSBAnswerHookInteger`, `AACSBAnswerHookDouble`, selected by `AACSBThunkForReturnType`). Anything whose return type cannot be forwarded (structs/C++ types) is `SKIPPED` with that reason instead of being hooked with a wrong ABI.
- TWO MORE ABI SAFETY RULES THAT CAME WITH THE RELAXED GATE: a `float`-returning method is forwarded through a real `float` thunk (never through the `double` thunk, whose low 32 bits are not the original float's bit pattern), and selectors in an ARC method family (`init`/`new`/`copy`/`mutableCopy`/`alloc`-style first component) are never hooked, registered or invoked, because the caller assumes a +1 return value there and an ARC-compiled thunk would return it as autoreleased. Both are `SKIPPED` with the reason written into the discovery file.
- MSHookMessageEx IS NOW THE INTENDED MECHANISM: the prototype is declared locally (no private header dependency) and resolved with `dlsym(RTLD_DEFAULT, "MSHookMessageEx")` so the tweak never hard-links the symbol; the successful original IMP comes from its out-parameter. When the symbol is absent in a process, the same removal-with-saved-original contract is implemented with `method_setImplementation`, and the mechanism actually used is written per hook. `tests/source_checks.py` and `tests/deb_check.py` no longer forbid `MSHookMessageEx`; the assertion was inverted with a comment explaining why (it is the ElleKit/substrate-compat hooking primitive this version is built on).
- ARGUMENT-TAKING METHODS ARE NOT HOOKED — THEY ARE INVOCATION CANDIDATES: a C replacement cannot rebuild an arbitrary ABI's arguments, so those methods are registered instead. At answer time the module locates a live instance of that class through the existing bounded window / view-controller / responder scan and calls the method with `NSInvocation` built from the runtime method signature, passing nil/0 default arguments (`AACSBMethodInvocationSafe`, `AACSBInvocationArgumentSafe`, `AACSBInvokeByInvocation`, `AACSBInvocationSelectorFor`). Bounds and safety: at most 3 explicit arguments, only argument types whose default value can be constructed, a hard blacklist so no decline/reject/hang-up selector is ever hooked, registered or invoked, a per-(class,selector) registration key, a 12-candidate cap, and the pre-existing speech-recursion guard (`AACSBInvoking`/`AACSBDepth`) around the invocation.
- PER-METHOD OUTCOME, IN THE DISCOVERY FILE AND IN THE LOG: every candidate method gets exactly one recorded outcome — `HOOKED` (with `abi=` and `mechanism=` and the original IMP), `INVOKABLE_BY_INVOCATION` (with args/return), `CAPTURED` (live instance seen), `INVOKED_BY_INVOCATION` (the answer step really used it, with the result), or `SKIPPED reason=<concrete reason>`. The header line `# HOOKED_TOTAL hooked=<n> invokable=<n> answerPaths=<n> of candidateClasses=<n> rejected=<n> invokableSkipped=<n> invocationAttempts=<n> rescanVisited=<n> discoverRuns=<n> globalPassScanned=<n>`, the `HOOK_SUMMARY`/`HOOK_ENTRY` and `INVOKE_SUMMARY`/`INVOKE_ENTRY` lines and the `# CONCLUSIVE:` line make the next device test conclusive without guessing. The same summary is also written to the shared log by `AACSBLogMethodOutcomes` immediately before an answer is attempted.
- TWO DISCOVERY PASSES + TIMED RETRIES: the keyword pass (`AACSBClassKeywords`, extended with the modern phone-call UI families) runs first; if it produces no answer path at all, a bounded global pass scans runtime classes whose NAME contains "call" with a strict selector subset (no bare `accept`, so `-[NSXPCConnection acceptInputForMode:beforeDate:]`-style framework methods cannot become candidates), capped at 600 processed classes, 1.5 s wall-clock, and stopping once 8 answer paths exist. Discovery is also retried by a 3 s and a 12 s timer in addition to the existing call-event retry, because call-UI classes are usually registered after the dylib constructor.
- EVERY EXISTING SAFETY PROPERTY IS KEPT: no double hooking (per-(class,selector) key set **plus** a hooked-IMP set and an "is this already one of our thunks" check), explicit rollback that says whether it really rolled back, class/hook/selector caps, the recursion guard around our own invocations, the single-owner rule, per-UUID single submission, fail-closed configuration, and the stop latch.
- FULL RUN-LOG SHARING (new Settings entries): `分享全部运行日志` and `运行日志文件：逐项查看 / 分享` (Settings → the new 运行日志分享 group). They collect the per-host shared logs (`aac-incall.log`, `aac-springboard.log`, `aac-mobilephone.log`, `aac-settings.log`), the per-host runtime-discovery files (`aac-incall.discovery.txt`, `aac-springboard.discovery.txt`), the per-host inventories (`aac-<host>.txt`), the settings log, a freshly exported `configuration.plist`, the call-record text export, the CFPreferences fallback dumps and the probe-companion dump. Every expected path is listed with its REAL state (`存在`/`缺失`, size, readable) and, when missing, the reason (candidate directory unusable / the directory exists but that process never wrote it / cross-process visibility unverified). Existing, readable files are copied into a fresh temporary directory under flat unique names and handed to `UIActivityViewController` together with the report text; a per-row tap opens a readable text view and a per-row ⓘ shares only that file. Nothing is fabricated, no credential is included, and the report states that none of it proves answering works.
- CALLKIT ERROR MEANING CORRECTED: Apple's `CXErrorCodeRequestTransactionError` order is unknown(0), unentitled(1), unknownCallProvider(2), emptyTransaction(3), unknownCallUUID(4), callUUIDAlreadyExists(5), invalidAction(6), maximumCallGroupsReached(7). ## 1.11.0 SpringBoard answer path (historical; superseded by 1.12.0)

1.11.0 keeps every 1.9.x/1.10.0 guard (fail-closed configuration validity, plugin stop latch plus explicit resume, exact-match exclusion list, decimal seconds editor, audio library, records list, icon, multi-path shared log, per-process Darwin probes, artifact checks) and the injection filter shipped exactly `com.apple.mobilephone` and `com.apple.springboard` (1.12.0 ships four ids, see above). - SpringBoard retains its own `CXCallObserver` + `CXCallController` and learns the incoming call UUID and state from the public CallKit properties.
- RUNTIME DISCOVERY: on load the SpringBoard module enumerates `objc_getClassList` (bounded to 400 candidate classes) and matches class names containing `IncomingCall`, `CallAlert`, `CallToAction`, `CallPresentation`, `InCall`, `SBInCall`, `LockScreenCall`, `AnswerCall`, `CallController`, `CallUI`, plus `SBLockScreen*` names containing call/answer. For each candidate class it walks `class_copyMethodList` and collects instance selectors containing answer/accept/pickUp.
- DYNAMIC HOOK: only selectors whose ABI is provable are hooked — exactly two Objective-C arguments (self + `_cmd`) and a `void` return type — so the fixed-signature interposer `AACSBAnswerHook(id,SEL)` is ABI-correct and passing through to the saved original IMP is behaviour-neutral. - CAPTURE: the hook records the receiving object and the selector into the discovery record and into the shared log. The live object is kept in a weak reference plus a strong reference that is released after a bounded 180-second hold; if neither is alive at answer time the module re-scans the window/scene view hierarchy, view-controller children/presented controllers and responder chains (bounded to 4000 nodes / depth 30) for an instance of any hooked class.
- POLICY: the first eligible incoming-call event runs the unchanged policy — fail-closed `ConfigVersion` validation, stop latch, mode 2 only, exact-normalised exclusion list (unknown number with a non-empty list refuses), and the configured N seconds. After the delay the call is re-checked as still incoming/unanswered (`AACMaySubmit` generation check, `hasConnected`/`hasEnded`) and the settings are re-read (log line `SpringBoard re-verify before answering: ... configValid=...`), then the discovered UI object's own method is invoked by calling the saved ORIGINAL IMP directly, with `AACSBInvoking`/`AACSBDepth` recursion guards so the hook cannot re-enter the policy.
- LOG-ONLY FALLBACK: if no ABI-provable method exists, or no live object can be captured/re-found, the module logs `LOG-ONLY primary path: ...` and records `未发现可调用的 UI 接听路径（仅日志）`; it then makes one clearly labelled secondary attempt with the public `CXAnswerCallAction` transaction (authorization not guaranteed). ## Actual answer implementation (phone module, unchanged)
