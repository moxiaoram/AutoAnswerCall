# AutoAnswerCall 1.13.0

Package: com.autoanswer.call. BuildID is supplied in the delivery report using the compiled commit and successful CI run. No installation, live system-setting change, calls, or device runtime validation performed for 1.13.0; the InCallService/SpringBoard answer paths are unverified on device.

## 1.13.0 Relaxed hook ABI gate + full run-log sharing (NOT device-verified)

1.13.0 keeps every 1.9.x/1.10.0/1.11.0/1.12.0 guard (fail-closed `ConfigVersion` validation, plugin stop latch plus explicit resume, mode 2, exact-match exclusion list, decimal seconds editor, audio library, records list, icon, multi-path shared log, per-process Darwin probes, per-host probe/pong/discovery names, deterministic single-owner role table with a per-UUID submission guard, artifact checks) and fixes the two things the last device test exposed.

DEVICE EVIDENCE THAT DROVE IT (iOS 17.3 RootHide, user's screenshots): the SpringBoard module is injected and its probes/pongs arrive, `MobilePhone` and `InCallService` never announced themselves, the incoming test call WAS detected by SpringBoard with the correct delay policy, and then the record said `未发现可调用的 UI 接听路径（仅日志）` while the public transaction fallback failed with `com.apple.CallKit.error.requesttransaction` code 1. Since nothing was hooked at all, the hook ABI gate itself — not the class list — was the most likely reason nothing could answer.

- HOOK ABI GATE RELAXED (`AACSpringBoard.h`): 1.12.0 hooked only `(self,_cmd)`-shaped, void-returning methods because its replacement had a fixed C signature. That gate is gone. The accepted set is now **zero explicit arguments with ANY return type a fixed thunk can forward correctly** (void / BOOL / object / integer / float), each with its own thunk, so the saved original IMP is called with the right signature and behaviour is unchanged (`AACSBAnswerHook`, `AACSBAnswerHookBool`, `AACSBAnswerHookObject`, `AACSBAnswerHookInteger`, `AACSBAnswerHookDouble`, selected by `AACSBThunkForReturnType`). Anything whose return type cannot be forwarded (structs/C++ types) is `SKIPPED` with that reason instead of being hooked with a wrong ABI.
- TWO MORE ABI SAFETY RULES THAT CAME WITH THE RELAXED GATE: a `float`-returning method is forwarded through a real `float` thunk (never through the `double` thunk, whose low 32 bits are not the original float's bit pattern), and selectors in an ARC method family (`init`/`new`/`copy`/`mutableCopy`/`alloc`-style first component) are never hooked, registered or invoked, because the caller assumes a +1 return value there and an ARC-compiled thunk would return it as autoreleased. Both are `SKIPPED` with the reason written into the discovery file.
- MSHookMessageEx IS NOW THE INTENDED MECHANISM: the prototype is declared locally (no private header dependency) and resolved with `dlsym(RTLD_DEFAULT, "MSHookMessageEx")` so the tweak never hard-links the symbol; the successful original IMP comes from its out-parameter. When the symbol is absent in a process, the same removal-with-saved-original contract is implemented with `method_setImplementation`, and the mechanism actually used is written per hook. `tests/source_checks.py` and `tests/deb_check.py` no longer forbid `MSHookMessageEx`; the assertion was inverted with a comment explaining why (it is the ElleKit/substrate-compat hooking primitive this version is built on).
- ARGUMENT-TAKING METHODS ARE NOT HOOKED — THEY ARE INVOCATION CANDIDATES: a C replacement cannot rebuild an arbitrary ABI's arguments, so those methods are registered instead. At answer time the module locates a live instance of that class through the existing bounded window / view-controller / responder scan and calls the method with `NSInvocation` built from the runtime method signature, passing nil/0 default arguments (`AACSBMethodInvocationSafe`, `AACSBInvocationArgumentSafe`, `AACSBInvokeByInvocation`, `AACSBInvocationSelectorFor`). Bounds and safety: at most 3 explicit arguments, only argument types whose default value can be constructed, a hard blacklist so no decline/reject/hang-up selector is ever hooked, registered or invoked, a per-(class,selector) registration key, a 12-candidate cap, and the pre-existing speech-recursion guard (`AACSBInvoking`/`AACSBDepth`) around the invocation.
- PER-METHOD OUTCOME, IN THE DISCOVERY FILE AND IN THE LOG: every candidate method gets exactly one recorded outcome — `HOOKED` (with `abi=` and `mechanism=` and the original IMP), `INVOKABLE_BY_INVOCATION` (with args/return), `CAPTURED` (live instance seen), `INVOKED_BY_INVOCATION` (the answer step really used it, with the result), or `SKIPPED reason=<concrete reason>`. The header line `# HOOKED_TOTAL hooked=<n> invokable=<n> answerPaths=<n> of candidateClasses=<n> rejected=<n> invokableSkipped=<n> invocationAttempts=<n> rescanVisited=<n> discoverRuns=<n> globalPassScanned=<n>`, the `HOOK_SUMMARY`/`HOOK_ENTRY` and `INVOKE_SUMMARY`/`INVOKE_ENTRY` lines and the `# CONCLUSIVE:` line make the next device test conclusive without guessing. The same summary is also written to the shared log by `AACSBLogMethodOutcomes` immediately before an answer is attempted.
- TWO DISCOVERY PASSES + TIMED RETRIES: the keyword pass (`AACSBClassKeywords`, extended with the modern phone-call UI families) runs first; if it produces no answer path at all, a bounded global pass scans runtime classes whose NAME contains "call" with a strict selector subset (no bare `accept`, so `-[NSXPCConnection acceptInputForMode:beforeDate:]`-style framework methods cannot become candidates), capped at 600 processed classes, 1.5 s wall-clock, and stopping once 8 answer paths exist. Discovery is also retried by a 3 s and a 12 s timer in addition to the existing call-event retry, because call-UI classes are usually registered after the dylib constructor.
- EVERY EXISTING SAFETY PROPERTY IS KEPT: no double hooking (per-(class,selector) key set **plus** a hooked-IMP set and an "is this already one of our thunks" check), explicit rollback that says whether it really rolled back, class/hook/selector caps, the recursion guard around our own invocations, the single-owner rule, per-UUID single submission, fail-closed configuration, and the stop latch.
- FULL RUN-LOG SHARING (new Settings entries): `分享全部运行日志` and `运行日志文件：逐项查看 / 分享` (Settings → the new 运行日志分享 group). They collect the per-host shared logs (`aac-incall.log`, `aac-springboard.log`, `aac-mobilephone.log`, `aac-settings.log`), the per-host runtime-discovery files (`aac-incall.discovery.txt`, `aac-springboard.discovery.txt`), the per-host inventories (`aac-<host>.txt`), the settings log, a freshly exported `configuration.plist`, the call-record text export, the CFPreferences fallback dumps and the probe-companion dump. Every expected path is listed with its REAL state (`存在`/`缺失`, size, readable) and, when missing, the reason (candidate directory unusable / the directory exists but that process never wrote it / cross-process visibility unverified). Existing, readable files are copied into a fresh temporary directory under flat unique names and handed to `UIActivityViewController` together with the report text; a per-row tap opens a readable text view and a per-row ⓘ shares only that file. Nothing is fabricated, no credential is included, and the report states that none of it proves answering works.
- CALLKIT ERROR MEANING CORRECTED: Apple's `CXErrorCodeRequestTransactionError` order is unknown(0), unentitled(1), unknownCallProvider(2), emptyTransaction(3), unknownCallUUID(4), callUUIDAlreadyExists(5), invalidAction(6), maximumCallGroupsReached(7). Code 1 therefore means **unentitled** ("The app doesn't have the entitlement to perform the actions in the requested transaction") — the 1.12.0 table said `unknownCallUUID` and was wrong; the table, the log/record text, the Root.plist footers and the tests are corrected. Apple also documents `requestTransaction` as asking the telephony provider to perform the actions and `CXAnswerCallAction` as performed by a CallKit provider, which is a second, independent reason a tweak process cannot use that path: it stays exactly ONE clearly labelled diagnostic attempt, never the answering plan.
- HONEST LIMITATIONS: still UNVERIFIED on device. The relaxed gate makes the previous "nothing hooked" outcome much less likely, but whether the real iOS 17.3 answer entry now matches a thunk-able or invocation-able candidate, and whether invoking it with default arguments is safe and effective, can only be decided by the next device call + the discovery file. If the next discovery file still reports zero answer paths, that file now says exactly why for every candidate, which is the point of this version.

## 1.12.0 InCallService answer host + single-owner arbitration (NOT device-verified)

1.12.0 keeps every 1.9.x/1.10.0/1.11.0 guard (fail-closed `ConfigVersion` validation, plugin stop latch plus explicit resume button, mode 2, exact-match exclusion list, decimal seconds editor, audio library, records list, icon, multi-path shared log, per-process Darwin probes, artifact checks) and generalises the 1.11.0 SpringBoard-only answer module into a host-parameterised module driven by a host table.

Device evidence that motivated it (iOS 17.3 RootHide, real test call at 19:46:53): the SpringBoard host was injected, detected the call (UUID recorded), ran the configured 6 s delay and the policy layer correctly — then at 19:47:00 it recorded `未发现可调用的 UI 接听路径（仅日志）；已尝试次要的公开事务路径` and the secondary public transaction failed with `com.apple.CallKit.error.requesttransaction` **code 1**, which 1.12.0 mis-mapped as `unknownCallUUID` (1.13.0 corrects it to `unentitled`, see above), and the call ended unanswered. So: (1) detection + delay + policy work; (2) SpringBoard had no ABI-provable hookable answer UI under the 1.12.0 gate; (3) the public `CXAnswerCallAction` path is effectively dead on this device for a tweak process.

- HOST TABLE (`AACAnswerHost.h`): `{bundle id, process name, probe name, pong name, discovery file name}` for `incall` (InCallService, bundle `com.apple.InCallService`, probe `com.autoanswer.call.probe.incall`, pong `com.autoanswer.call.pong.incall`, discovery `aac-incall.discovery.txt`, priority 2), `springboard` (unchanged 1.11.0 names, priority 1), `mobilephone` (legacy pong `com.autoanswer.call.pong`, priority 0, not an answer host) and `settings`.
- SAME MACHINERY, MULTIPLE HOSTS: `AACSpringBoard.h` is now the host-parameterised module. `AACSBEnv.host` supplies the process tag, display name, discovery file name, priority and answer capability; the discovery/hook/capture/delay/policy/recursion-guard code path is byte-identical for InCallService and SpringBoard. `AACSBProcess()` returns the host tag, so the probe name (`com.autoanswer.call.probe.<tag>`) and the discovery file (`aac-<tag>.discovery.txt`) follow the host automatically.
- SINGLE OWNER: every host may OBSERVE and RECORD, but exactly one host submits an answer. Role table (strongest first): `InCallService(2) > SpringBoard(1) > 仅日志(0)`. A host is a candidate owner only if its own runtime discovery found an ABI-provable hookable method; the highest-priority candidate whose higher-priority peers have not been observed wins. Peer liveness is evidence-based: every host observes every other host's probe notification (the 1.10.0/1.11.0 probes are proven to cross process boundaries on this device) and every answer host's ownership claim `com.autoanswer.call.owner.<tag>`; a probe/claim seen within 90 s counts as present. Non-owners record `observer only, answer owned by <host>` and never submit. The decision is re-evaluated immediately before answering (`AACSBShouldAnswer`), so a host that was the owner demotes itself when InCallService appears later, and a per-host answered-UUID set (`AACSBClaimAnswerUUID`) refuses a second submission for the same call UUID.
- InCallService host: registers its own probe/pong Darwin names, writes its own discovery file through the existing multi-path shared log, runs the same runtime discovery + dynamic hook + capture + hierarchy re-scan, and uses its own `CXCallObserver` (public CallKit) for UUID/state. Its discovery file header states `host=`, `role=`, `owner=`, `roleTable=`, plus `HOOKED_TOTAL`, `HOOK_SUMMARY`, one `HOOK_ENTRY` per hooked class+selector, per-class `CLASS <name> methods=<n>` lines, per-method `SKIP <sel> reason=...`, and either a `# CONCLUSIVE: 本宿主已挂钩...` or `# CONCLUSIVE: ...可挂钩接听方法=0，因此本宿主不可能接听` line, so the next device test is conclusive about which host can answer.
- CALLKIT ERROR DECODING (1.13.0 correction): the 1.12.0 mapping of `com.apple.CallKit.error.requesttransaction` code 1 as `unknownCallUUID` was WRONG and is fixed in 1.13.0 to `unentitled`. See the 1.13.0 section above; `com.apple.CallKit.error.incomingcall` (1 unentitled, 2 callUUIDAlreadyExists, 3 filteredByDoNotDisturb, 4 filteredByBlockList) was already correct, and anything else is still reported as "未记录/未知错误（不猜测含义）".
- PUBLIC TRANSACTION FALLBACK IS NOT THE PLAN: it stays exactly one clearly-labelled diagnostic attempt after the primary path fails, now annotated with the decoded code; nothing is retried and no weight is added to it, because it is proven ineffective here.
- INJECTION FILTER is exactly four ids: `com.apple.mobilephone`, `com.apple.springboard`, `com.apple.InCallService`, `com.apple.incallservice`. The lowercase-only rule still applies to the phone id; the two InCall spellings only cover case differences and duplicate/nonexistent ids are harmless. `INSTALL_TARGET_PROCESSES` additionally lists `InCallService`. `com.apple.MobilePhone` is never written to the filter and is accepted only as the pre-existing runtime fallback (together with the `MobilePhone`/`SpringBoard`/`InCallService` process-name fallbacks).
- SETTINGS: the 进程探测 page lists the new `incall` probe row and its pong counter (`com.autoanswer.call.pong.incall`) alongside the phone/SpringBoard counters; the discovery section reads ANY host discovery file that exists (InCallService first, then SpringBoard), labels the host and the exact path for every row, shows the owning role read out of the file, and keeps the honest `没有可读的发现文件` fallback instead of inventing a result.
- HONEST LIMITATIONS: this is still UNVERIFIED on device. Whether answering can fire depends on the discovery files (`aac-incall.discovery.txt` / `aac-springboard.discovery.txt`) on the real device. If InCallService is also not injectable on that jailbreak, that is a finding to report, not to paper over — the log and the probe page will show that InCallService never announced itself, exactly as the phone process never did.

## 1.11.0 SpringBoard answer path (historical; superseded by 1.12.0)

1.11.0 keeps every 1.9.x/1.10.0 guard (fail-closed configuration validity, plugin stop latch plus explicit resume, exact-match exclusion list, decimal seconds editor, audio library, records list, icon, multi-path shared log, per-process Darwin probes, artifact checks) and the injection filter shipped exactly `com.apple.mobilephone` and `com.apple.springboard` (1.12.0 ships four ids, see above). The answer path moves to SpringBoard because the 1.10.0 probe build produced device evidence that the SpringBoard module loads and posts its Darwin notification, while the phone app process never announced itself and never created `aac-mobilephone.log`.

- SpringBoard retains its own `CXCallObserver` + `CXCallController` and learns the incoming call UUID and state from the public CallKit properties.
- RUNTIME DISCOVERY: on load the SpringBoard module enumerates `objc_getClassList` (bounded to 400 candidate classes) and matches class names containing `IncomingCall`, `CallAlert`, `CallToAction`, `CallPresentation`, `InCall`, `SBInCall`, `LockScreenCall`, `AnswerCall`, `CallController`, `CallUI`, plus `SBLockScreen*` names containing call/answer. For each candidate class it walks `class_copyMethodList` and collects instance selectors containing answer/accept/pickUp.
- DYNAMIC HOOK: only selectors whose ABI is provable are hooked — exactly two Objective-C arguments (self + `_cmd`) and a `void` return type — so the fixed-signature interposer `AACSBAnswerHook(id,SEL)` is ABI-correct and passing through to the saved original IMP is behaviour-neutral. Each hook stores its original IMP keyed by (class, selector); the same selector or the same IMP is never hooked twice (`AACSBHookedKeys`, `AACSBHookedIMPs`), and any failed/double hook is rolled back. Hook count is capped at 24 per run and the enumeration can re-run at most 3 times (a call event with nothing hooked triggers one bounded retry, because the class list can grow as frameworks load).
- CAPTURE: the hook records the receiving object and the selector into the discovery record and into the shared log. The live object is kept in a weak reference plus a strong reference that is released after a bounded 180-second hold; if neither is alive at answer time the module re-scans the window/scene view hierarchy, view-controller children/presented controllers and responder chains (bounded to 4000 nodes / depth 30) for an instance of any hooked class.
- POLICY: the first eligible incoming-call event runs the unchanged policy — fail-closed `ConfigVersion` validation, stop latch, mode 2 only, exact-normalised exclusion list (unknown number with a non-empty list refuses), and the configured N seconds. After the delay the call is re-checked as still incoming/unanswered (`AACMaySubmit` generation check, `hasConnected`/`hasEnded`) and the settings are re-read (log line `SpringBoard re-verify before answering: ... configValid=...`), then the discovered UI object's own method is invoked by calling the saved ORIGINAL IMP directly, with `AACSBInvoking`/`AACSBDepth` recursion guards so the hook cannot re-enter the policy.
- LOG-ONLY FALLBACK: if no ABI-provable method exists, or no live object can be captured/re-found, the module logs `LOG-ONLY primary path: ...` and records `未发现可调用的 UI 接听路径（仅日志）`; it then makes one clearly labelled secondary attempt with the public `CXAnswerCallAction` transaction (authorization not guaranteed). Nothing is ever reported as answered on the strength of our own call. The record and the log only say `observed connection` when `CXCall.hasConnected` is actually reported.
- The Settings 环境清单 page (AACProbeController) gained a `SpringBoard 运行时发现/挂钩结果 (runtime-discovered)` section that READS `aac-springboard.discovery.txt` written by the SpringBoard module, shows how many methods were hooked and lets the user open the full class/method/skip-reason list. If the file is missing it says so instead of inventing a result.
- HONEST LIMITATION, REPORTED BY THE BUILD ITSELF: the SpringBoard answer path is UNVERIFIED on device. Whether it works depends entirely on which private incoming-call UI class actually exists at runtime on that iOS 17.3 build; the tweak does not require any specific class name, and when nothing matching exists it degrades to log-only rather than claiming success. The 1.11.0 discovery file is the artifact that tells the next device test what really exists.

## Modes

- Scheme 2 (Mode=2, default): plugin exclusion whitelist priority. Enabled is read separately and on delayed revalidation. Disable iOS native Auto-Answer Calls manually first: Settings > Accessibility > Touch > Call Audio Routing > Auto-Answer Calls. Only the separate guarded native-off action may invoke the system setter; ordinary plugin policy never changes it. Full normalized numbers match exactly; formatting spaces, parentheses, dots, dashes and an initial + are removed. Country prefixes are not inferred, suffix/substring/wildcard matching is not supported. Comma, Chinese comma, semicolon and newline separate entries. - Scheme 1 (Mode=1): native iOS fallback guidance. The plugin submits no answer transaction. Open the system settings with the button or follow the manual path above. The deep link is unverified and may fail. Native iOS auto-answer applies to all calls and is independent of the plugin Enabled switch, delay and whitelist. Switching the plugin off cannot turn off the system feature.

## Actual answer implementation (phone module, unchanged)

In InCallService and SpringBoard (1.11.0/1.12.0 answer hosts) the answer step is instead the runtime-discovered UI method described in the sections above, executed by the single highest-priority host that actually found a hookable method; the paragraph below describes the MobilePhone module, which is byte-for-byte the 1.10.0 behaviour.

MobilePhone alone retains a CXCallObserver and a delegate implementing callObserver:callChanged: with CXCall. Incoming/outgoing, connected, ended and UUID use public properties. Each UUID schedules at most one outstanding delay and at most one transaction attempt; delayed work looks up the current call again and rereads preferences. It submits CXAnswerCallAction with that UUID through CXCallController requestTransaction:completion:. Completion failures include domain, code and description. Transaction acceptance is not connection success. Connection observed without a pending request is labelled manual/system/other; connection during a pending request is logged as correlation only, because manual/system answering can coincide. Pending observations time out after 15 seconds.

CXCall has no public number property. Optional phoneNumber/callerNumber selectors are only called when an existing getter has exactly two Objective-C ABI arguments and object return type, and its result is an NSString; otherwise the number is unknown. These are not guaranteed to exist. With a nonempty exclusion list this normally means fail closed until a validated number source exists on the actual device. No guessed CTCall/IOBluetooth hooks remain. Public CallKit transactions do not guarantee cellular answering permissions. Retaining an observer in MobilePhone cannot prevent suspension; background/lockscreen delivery is not guaranteed. Injection scope is now the filter's two official ids (com.apple.mobilephone, com.apple.springboard); the runtime-compatible wrong-case phone id is only a fallback inside the dylib.

## Audio

Import uses UIDocumentPicker asCopy:YES, starts/stops security scope, coordinates reads on a background worker, and reads at most 5MB + 1 byte. Empty, oversized or unsupported files fail with source-read, destination-write or audio-decoder details. Successful files go into the actual Settings process Application Support/AutoAnswerCall directory, followed by an independent audio.plist. Local AVAudioPlayer preview retains the player and checks prepare/play return values. The settings diagnostic displays imported name, byte count and path. Export persistent configuration uses the share sheet to export configuration.plist.

The selected AudioPath preference is also published as configuration. This does not grant MobilePhone access to the Settings sandbox. Phone-side local playback is optional, default off, and logs inaccessible/unsupported files. In 1.9.1 and 1.10.0 every observed connection conservatively suppresses automatic local playback because this observer/transaction path cannot prove who answered. A connection before submission invalidates the UUID generation and prevents its timer from submitting; expiry also requeries connected/ended. Later transaction completion cannot clear the sticky suppression. Existing imported audio and Settings preview remain available; suppression never deletes audio files. Already-submitted transactions cannot be revoked, and a simultaneous human/system answer cannot be deterministically distinguished. 1.10.0 does not assume any RootHide shared path exists: the /var/jb-prefixed directory is only one candidate that is attempted and reported per process, and every claim about it stays inside the per-path evidence report. No audio bytes are pushed through CFPreferences. Local AVAudioPlayer is NOT call uplink injection and cannot promise the remote party hears it.

## Diagnostics

Settings logs persist to its own Application Support/AutoAnswerCall/settings.log with error reporting. Those records prove only the Settings module. Phone logs use NSLog plus a separate CFPreferences domain com.autoanswer.call.phone; writes report failure and cross-sandbox visibility is not guaranteed. Phone diagnostics explicitly show missing/inaccessible data. Darwin ping/pong probes only whether MobilePhone responds at that moment; absence can mean suspension, no injection or notification restrictions, and a pong does not validate call privileges. No settings preview is claimed to prove phone loading or call functionality.
