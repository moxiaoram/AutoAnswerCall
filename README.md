# AutoAnswerCall 1.11.0

Package: com.autoanswer.call. BuildID is supplied in the delivery report using the compiled commit and successful CI run. No installation, live system-setting change, calls, or device runtime validation performed for 1.10.0 or 1.11.0; the 1.11.0 SpringBoard answer path is unverified on device.

## 1.11.0 SpringBoard answer path (runtime discovery, NOT device-verified)

1.11.0 keeps every 1.9.x/1.10.0 guard (fail-closed configuration validity, plugin stop latch plus explicit resume, exact-match exclusion list, decimal seconds editor, audio library, records list, icon, multi-path shared log, per-process Darwin probes, artifact checks) and the injection filter still ships exactly `com.apple.mobilephone` and `com.apple.springboard`. The answer path moves to SpringBoard because the 1.10.0 probe build produced device evidence that the SpringBoard module loads and posts its Darwin notification, while the phone app process never announced itself and never created `aac-mobilephone.log`.

- SpringBoard retains its own `CXCallObserver` + `CXCallController` and learns the incoming call UUID and state from the public CallKit properties.
- RUNTIME DISCOVERY: on load the SpringBoard module enumerates `objc_getClassList` (bounded to 400 candidate classes) and matches class names containing `IncomingCall`, `CallAlert`, `CallToAction`, `CallPresentation`, `InCall`, `SBInCall`, `LockScreenCall`, `AnswerCall`, `CallController`, `CallUI`, plus `SBLockScreen*` names containing call/answer. For each candidate class it walks `class_copyMethodList` and collects instance selectors containing answer/accept/pickUp.
- DYNAMIC HOOK: only selectors whose ABI is provable are hooked — exactly two Objective-C arguments (self + `_cmd`) and a `void` return type — so the fixed-signature interposer `AACSBAnswerHook(id,SEL)` is ABI-correct and passing through to the saved original IMP is behaviour-neutral. Each hook stores its original IMP keyed by (class, selector); the same selector or the same IMP is never hooked twice (`AACSBHookedKeys`, `AACSBHookedIMPs`), and any failed/double hook is rolled back. Hook count is capped at 24 per run and the enumeration can re-run at most 3 times (a call event with nothing hooked triggers one bounded retry, because the class list can grow as frameworks load).
- CAPTURE: the hook records the receiving object and the selector into the discovery record and into the shared log. The live object is kept in a weak reference plus a strong reference that is released after a bounded 180-second hold; if neither is alive at answer time the module re-scans the window/scene view hierarchy, view-controller children/presented controllers and responder chains (bounded to 4000 nodes / depth 30) for an instance of any hooked class.
- POLICY: the first eligible incoming-call event runs the unchanged policy — fail-closed `ConfigVersion` validation, stop latch, mode 2 only, exact-normalised exclusion list (unknown number with a non-empty list refuses), and the configured N seconds. After the delay the call is re-checked as still incoming/unanswered (`AACMaySubmit` generation check, `hasConnected`/`hasEnded`) and the settings are re-read (log line `SpringBoard re-verify before answering: ... configValid=...`), then the discovered UI object's own method is invoked by calling the saved ORIGINAL IMP directly, with `AACSBInvoking`/`AACSBDepth` recursion guards so the hook cannot re-enter the policy.
- LOG-ONLY FALLBACK: if no ABI-provable method exists, or no live object can be captured/re-found, the module logs `LOG-ONLY primary path: ...` and records `未发现可调用的 UI 接听路径（仅日志）`; it then makes one clearly labelled secondary attempt with the public `CXAnswerCallAction` transaction (authorization not guaranteed). Nothing is ever reported as answered on the strength of our own call. The record and the log only say `observed connection` when `CXCall.hasConnected` is actually reported.
- The Settings 环境清单 page (AACProbeController) gained a `SpringBoard 运行时发现/挂钩结果 (runtime-discovered)` section that READS `aac-springboard.discovery.txt` written by the SpringBoard module, shows how many methods were hooked and lets the user open the full class/method/skip-reason list. If the file is missing it says so instead of inventing a result.
- HONEST LIMITATION, REPORTED BY THE BUILD ITSELF: the SpringBoard answer path is UNVERIFIED on device. Whether it works depends entirely on which private incoming-call UI class actually exists at runtime on that iOS 17.3 build; the tweak does not require any specific class name, and when nothing matching exists it degrades to log-only rather than claiming success. The 1.11.0 discovery file is the artifact that tells the next device test what really exists.

## 1.10.0 cross-process evidence build (no behaviour change)

1.10.0 is an EVIDENCE-GATHERING release. It does not change answer behaviour and it does not claim that automatic answering works. Every 1.9.x safety guard below is retained unchanged.

- Injection filter now lists BOTH official, case-sensitive bundle ids: `com.apple.mobilephone` and `com.apple.springboard`. The historical wrong-case `com.apple.MobilePhone` is accepted only as a runtime compatibility fallback inside the dylib and is never written into the filter plist.
- Each loaded module posts a Darwin notification on load and then every ~20 seconds. Darwin notifications carry no payload, so each process has its OWN name: `com.autoanswer.call.probe.mobilephone` / `com.autoanswer.call.probe.springboard`. A best-effort companion record is written to the own-domain CFPreferences key `LastProbe.<process>` (`com.autoanswer.call.probe`); its cross-process visibility is not claimed. A module loaded in any other process reports that fact and runs no module logic.
- Shared log channel: each process tries real absolute candidate directories in order — `/var/mobile/Library/Application Support/AutoAnswerCall`, `/var/jb/var/mobile/Library/Application Support/AutoAnswerCall`, the process container `Application Support/AutoAnswerCall`, `NSTemporaryDirectory()/AutoAnswerCall`, `/tmp/AutoAnswerCall` — keeps the first one that is actually writable IN THAT PROCESS, and logs which one was chosen plus every failure. If none is writable it falls back to the own-domain CFPreferences domain `com.autoanswer.call.sharelog` (`Log.<process>`). Every line is also sent to NSLog. Write failures never throw. No cross-process visibility is asserted anywhere: the Settings page reports the per-path result of every candidate as seen from the Settings process only.
- SpringBoard module: on load it enumerates the real runtime instead of guessing — `objc_getClassList` filtered to class names containing `IncomingCall`, `CallAlert`, `CallToAction`, `CallController`, `InCallService`, `AnswerCall`, `CallPresentation`, plus `SBLockScreen*` names containing call/answer. For each matching class it lists instance selectors containing answer/accept/pick/dial/connect. Bounded to 400 classes, 40 selectors per class and a 200000-character file cap with safe truncation. The full text is written next to the shared log as `aac-springboard.txt` and a bounded digest is appended to the shared log. NO hooks are installed and NO behaviour is changed by this module.
- Settings: new 进程探测 / 环境清单 page (per-process notification arrivals with timestamps since the page opened, legacy ping/pong record, a self-loopback test that only proves Darwin delivery inside the Settings process, and the per-path read/write report), and a 共享日志查看器 that tries every candidate path and displays whichever file is actually readable with the winning path label. It never fabricates readiness.
- Still not evidenced: injection into either process, in-process file writability on the device, delivery of callbacks while suspended or locked, cellular answer authorization, and any caller-number source. Nothing in this build may be read as "auto-answer works".

## 1.9.1 records and original icon

Root settings now exposes 自动接听记录 as an independent UITableViewController with pull-to-refresh, refresh button, latest-first rows, detail event timestamps and destructive clear confirmation. 电话模块诊断 remains a separate text diagnostic entry. No Settings preview or audio test can create a call record.

MobilePhone owns Records in CFPreferences domain com.autoanswer.call.phone. Each incoming CXCall UUID is the stable id; first-observed timestamp remains fixed, updated/result/status/events are upserted. At most 200 calls and 24 status changes per call are retained; repeated identical callbacks do not append an event. Outgoing calls are excluded. Scheduled, skipped, cancelled, submitted, accepted, failed (domain/code/detail), timeout, connected and ended are recorded from the actual state machine. Connected is observational and never proof of automatic attribution; transaction acceptance is never called connected. Number is only the ABI-checked optional getter result; otherwise the list explicitly shows unknown.

Settings synchronizes and reads the phone domain; absent/inaccessible data, empty arrays and failed synchronization are described honestly. A fresh ping times out after 2 seconds with possible suspension/injection/notification explanations. Cross-process CFPreferences may remain unavailable or stale even with a pong. Clear never writes from Settings: it sends a Darwin request, MobilePhone writes an empty array and checks synchronize plus its own readback before acknowledging. Failure or 3-second timeout reports deletion unconfirmed. Existing active states are suppressed after clear to avoid callbacks restoring old records; new call UUIDs are recorded normally. Acknowledgement confirms only phone-process write/readback, not filesystem durability or Settings cache visibility. Concurrent clear requests have no per-request nonce and use a shared domain-wide acknowledgement; they are intended for one Settings UI at a time.

Original icon.svg uses a blue gradient rounded square, curved white handset, clock and mint check dot; it does not reproduce the reference device/keypad artwork. Included PNGs are 8-bit RGBA, 29/58/87 px with transparent corners.

CI also compiles tests/records.m against macOS Foundation for UUID upsert, duplicate suppression, timestamp stability, unknown caller, acceptance/connection distinction, callback ordering truth, sorting/bounds, plist roundtrip and invalid record rejection. This is a model test, not iOS UI or real calls.

## 1.9 preserved behavior and explicit limits

- Delay is now a PSEditTextCell with a custom finite ASCII decimal parser, range 0..60 seconds, no slider. Invalid edits preserve the old value. Readback uses a decimal numeric string. Delay starts at the first eligible observed incoming CallKit delegate event, NOT measured audible ringing and NOT a startup snapshot. At expiry the call is looked up again and Enabled/mode/state/exclusions are reread. Unknown/unobserved calls do not schedule work.
- Stop plugin action writes Enabled=false and emits a plugin-only stop notification. Phone-side receipt increments a generation token to invalidate all unsubmitted old timers, and stops local playback. Notification delivery is not confirmed by posting. Already submitted transactions cannot be revoked. This action never changes the independent iOS native switch.
- Native pane button immediately attempts the publicly documented accessibility deep link prefs:root=ACCESSIBILITY&path=TOUCH_REACHABILITY_TITLE/CALL_AUDIO_ROUTING/callAudioRoutingAutoAnswer, without the old preliminary alert. Reference: https://github.com/FifiTheBulldog/ios-settings-urls/blob/master/settings-urls.md (Git blob 2ef8fa01af992b2d78ad926574f292b81c94af57). It remains UNVERIFIED on iOS17.3: URL completion confirms only that iOS accepted the URL, not arrival at the exact pane. Manual route: Settings > Accessibility > Touch > Call Audio Routing > Auto-Answer Calls. No guessed Preferences internal controller push is used.
- Native read/off adapter uses exact independently published AXSettings methods: +sharedInstance, -(bool)callAudioRoutingAutoAnswerEnabled, -(void)setCallAudioRoutingAutoAnswerEnabled:(bool). Source: https://github.com/nst/iOS-Runtime-Headers/blob/master/PrivateFrameworks/AccessibilityUtilities.framework/AXSettings.h (2018 header, not iOS17.3 evidence). Apple does not publish these as a supported public API; iOS17.3-specific runtime header portal is human-verification gated. Adapter dlopens the actual framework and requires exact argument counts, object factory return, B getter, v/B setter ABI on device before invoking anything. Missing/wrong ABI/exception => explicit unavailable, no write. Off re-reads after 0.4 seconds and reports only accessor readback. Persistence and native notification are owned by the native setter; NO guessed CFPreferences key/domain or notify name is written. Device ABI availability, cross-process cache invalidation and real effect are untested. This is guarded code, NOT a claim that one-click off works on the user's 17.3 device.
- Audio import preserves the coordinated asCopy/security-scoped/bounded 5MB-per-file pipeline that user confirmed works in 1.8. Multiple selection and repeated imports append UUID-named files; existing files are never replaced. audio-library.plist stores id/path/name/size/duration with SelectedAudioID. Existing audio.plist/AudioPath is registered in place without moving the old file. First import into an empty library selects the first entry; later imports retain selection. Settings audio list displays file name, size, duration, readability and selected checkmark. Tap a readable row to select, accessory button to preview/stop or confirm individual deletion. Deletion preserves files still referenced by another entry and selects the next entry when selected entry is deleted (or clears selected metadata if empty). Selected-only audio.plist/AudioPath/AudioName/AudioSize remain compatible; configuration export does not export all library entries/audio bytes. Library remains in the Settings sandbox; MobilePhone access/uplink is not solved.
- Tests include portable policy unit tests, source/structure checks, and tests/library.m compiled with macOS Foundation/AVFoundation against the actual shared library model (migration-in-place, persisted selection, append/no overwrite, shared-file retention, selected deletion and last-item cleanup, missing file removal, corrupt-library fail-closed), plus CI compile/link/sign/package. The model test is NOT iOS UIKit interaction, document picker/import runtime, device observer or live native-setting testing. No pong was observed here; screenshot or local preview is not call-function evidence.

## Modes

- Scheme 2 (Mode=2, default): plugin exclusion whitelist priority. Enabled is read separately and on delayed revalidation. Disable iOS native Auto-Answer Calls manually first: Settings > Accessibility > Touch > Call Audio Routing > Auto-Answer Calls. Only the separate guarded native-off action may invoke the system setter; ordinary plugin policy never changes it. Full normalized numbers match exactly; formatting spaces, parentheses, dots, dashes and an initial + are removed. Country prefixes are not inferred, suffix/substring/wildcard matching is not supported. Comma, Chinese comma, semicolon and newline separate entries. Invalid entries cause refusal; unknown caller with a nonempty whitelist also causes refusal.
- Scheme 1 (Mode=1): native iOS fallback guidance. The plugin submits no answer transaction. Open the system settings with the button or follow the manual path above. The deep link is unverified and may fail. Native iOS auto-answer applies to all calls and is independent of the plugin Enabled switch, delay and whitelist. Switching the plugin off cannot turn off the system feature.

## Actual answer implementation (phone module, unchanged)

In SpringBoard (added in 1.11.0) the answer step is instead the runtime-discovered UI method described in the 1.11.0 section above; the paragraph below describes the MobilePhone module, which is byte-for-byte the 1.10.0 behaviour.

MobilePhone alone retains a CXCallObserver and a delegate implementing callObserver:callChanged: with CXCall. Incoming/outgoing, connected, ended and UUID use public properties. Each UUID schedules at most one outstanding delay and at most one transaction attempt; delayed work looks up the current call again and rereads preferences. It submits CXAnswerCallAction with that UUID through CXCallController requestTransaction:completion:. Completion failures include domain, code and description. Transaction acceptance is not connection success. Connection observed without a pending request is labelled manual/system/other; connection during a pending request is logged as correlation only, because manual/system answering can coincide. Pending observations time out after 15 seconds.

CXCall has no public number property. Optional phoneNumber/callerNumber selectors are only called when an existing getter has exactly two Objective-C ABI arguments and object return type, and its result is an NSString; otherwise the number is unknown. These are not guaranteed to exist. With a nonempty exclusion list this normally means fail closed until a validated number source exists on the actual device. No guessed CTCall/IOBluetooth hooks remain. Public CallKit transactions do not guarantee cellular answering permissions. Retaining an observer in MobilePhone cannot prevent suspension; background/lockscreen delivery is not guaranteed. Injection scope is now the filter's two official ids (com.apple.mobilephone, com.apple.springboard); the runtime-compatible wrong-case phone id is only a fallback inside the dylib.

## Audio

Import uses UIDocumentPicker asCopy:YES, starts/stops security scope, coordinates reads on a background worker, and reads at most 5MB + 1 byte. Empty, oversized or unsupported files fail with source-read, destination-write or audio-decoder details. Successful files go into the actual Settings process Application Support/AutoAnswerCall directory, followed by an independent audio.plist. Local AVAudioPlayer preview retains the player and checks prepare/play return values. The settings diagnostic displays imported name, byte count and path. Export persistent configuration uses the share sheet to export configuration.plist.

The selected AudioPath preference is also published as configuration. This does not grant MobilePhone access to the Settings sandbox. Phone-side local playback is optional, default off, and logs inaccessible/unsupported files. In 1.9.1 and 1.10.0 every observed connection conservatively suppresses automatic local playback because this observer/transaction path cannot prove who answered. A connection before submission invalidates the UUID generation and prevents its timer from submitting; expiry also requeries connected/ended. Later transaction completion cannot clear the sticky suppression. Existing imported audio and Settings preview remain available; suppression never deletes audio files. Already-submitted transactions cannot be revoked, and a simultaneous human/system answer cannot be deterministically distinguished. 1.10.0 does not assume any RootHide shared path exists: the /var/jb-prefixed directory is only one candidate that is attempted and reported per process, and every claim about it stays inside the per-path evidence report. No audio bytes are pushed through CFPreferences. Local AVAudioPlayer is NOT call uplink injection and cannot promise the remote party hears it.

## Diagnostics

Settings logs persist to its own Application Support/AutoAnswerCall/settings.log with error reporting. Those records prove only the Settings module. Phone logs use NSLog plus a separate CFPreferences domain com.autoanswer.call.phone; writes report failure and cross-sandbox visibility is not guaranteed. Phone diagnostics explicitly show missing/inaccessible data. Darwin ping/pong probes only whether MobilePhone responds at that moment; absence can mean suspension, no injection or notification restrictions, and a pong does not validate call privileges. No settings preview is claimed to prove phone loading or call functionality.
